pg_continuous_archiving
pg continuous archiving · 3 steps · 87 source lines not turned into steps (shown grey, listed in the checklist as unmapped)
Source: https://www.postgresql.org/docs/18/continuous-archiving.html · Rights: PostgreSQL License; https://www.postgresql.org/about/licence/

Procedure text (blue = cited by a step)

7At all times, PostgreSQL maintains a write ahead log (WAL) in the pg_wal/ subdirectory of the cluster's data directory.
8The log records every change made to the database's data files.
9This log exists primarily for crash-safety purposes: if the system crashes, the database can be restored to consistency by “ replaying ” the log entries made since the last checkpoint.
10However, the existence of the log makes it possible to use a third strategy for backing up databases: we can combine a file-system-level backup with backup of the WAL files.
11If recovery is needed, we restore the file system backup and then replay from the backed-up WAL files to bring the system to a current state.
12This approach is more complex to administer than either of the previous approaches, but it has some significant benefits:
13We do not need a perfectly consistent file system backup as the starting point.
14Any internal inconsistency in the backup will be corrected by log replay (this is not significantly different from what happens during crash recovery).
15So we do not need a file system snapshot capability, just tar or a similar archiving tool.
16Since we can combine an indefinitely long sequence of WAL files for replay, continuous backup can be achieved simply by continuing to archive the WAL files.
17This is particularly valuable for large databases, where it might not be convenient to take a full backup frequently.
18It is not necessary to replay the WAL entries all the way to the end.
19We could stop the replay at any point and have a consistent snapshot of the database as it was at that time.
20Thus, this technique supports point-in-time recovery: it is possible to restore the database to its state at any time since your base backup was taken.
21If we continuously feed the series of WAL files to another machine that has been loaded with the same base backup file, we have a warm standby system: at any point we can bring up the second machine and it will have a nearly-current copy of the database.
22pg_dump and pg_dumpall do not produce file-system-level backups and cannot be used as part of a continuous-archiving solution.
23Such dumps are logical and do not contain enough information to be used by WAL replay.
24As with the plain file-system-backup technique, this method can only support restoration of an entire database cluster, not a subset.
25Also, it requires a lot of archival storage: the base backup might be bulky, and a busy system will generate many megabytes of WAL traffic that have to be archived.
26Still, it is the preferred backup technique in many situations where high reliability is needed.
27To recover successfully using continuous archiving (also called “ online backup ” by many database vendors), you need a continuous sequence of archived WAL files that extends back at least as far as the start time of your backup.
28So to get started, you should set up and test your procedure for archiving WAL files before you take your first base backup.
29Accordingly, we first discuss the mechanics of archiving WAL files.
30In an abstract sense, a running PostgreSQL system produces an indefinitely long sequence of WAL records.
31The system physically divides this sequence into WAL segment files, which are normally 16MB apiece (although the segment size can be altered during initdb).
32The segment files are given numeric names that reflect their position in the abstract WAL sequence.
33When not using WAL archiving, the system normally creates just a few segment files and then “ recycles ” them by renaming no-longer-needed segment files to higher segment numbers.
34It's assumed that segment files whose contents precede the last checkpoint are no longer of interest and can be recycled.
35When archiving WAL data, we need to capture the contents of each segment file once it is filled, and save that data somewhere before the segment file is recycled for reuse.
36Depending on the application and the available hardware, there could be many different ways of “ saving the data somewhere ”: we could copy the segment files to an NFS-mounted directory on another machine, write them onto a tape drive (ensuring that you have a way of identifying the original name of each file), or batch them together and burn them onto CDs, or something else entirely.
37To provide the database administrator with flexibility, PostgreSQL tries not to make any assumptions about how the archiving will be done.
38Instead, PostgreSQL lets the administrator specify a shell command or an archive library to be executed to copy a completed segment file to wherever it needs to go.
39This could be as simple as a shell command that uses cp, or it could invoke a complex C function — it's all up to you.
40To enable WAL archiving, set the wal_level configuration parameter to replica or higher, archive_mode to on, specify the shell command to use in the archive_command configuration parameter or specify the library to use in the archive_library configuration parameter.
41In practice these settings will always be placed in the postgresql.conf file.
42In archive_command, %p is replaced by the path name of the file to archive, while %f is replaced by only the file name.
43(The path name is relative to the current working directory, i.e., the cluster's data directory.) Use %% if you need to embed an actual % character in the command.
44The simplest useful command is something like:
45$ archive_command = 'test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f' # Unix
46$ archive_command = 'copy "%p" "C:\\server\\archivedir\\%f"' # Windows
47which will copy archivable WAL segments to the directory /mnt/server/archivedir.
48(This is an example, not a recommendation, and might not work on all platforms.) After the %p and %f parameters have been replaced, the actual command executed might look like this:
49$ test ! -f /mnt/server/archivedir/00000001000000A900000065 && cp pg_wal/00000001000000A900000065 /mnt/server/archivedir/00000001000000A900000065
50A similar command will be generated for each new file to be archived.
51The archive command will be executed under the ownership of the same user that the PostgreSQL server is running as.
52Since the series of WAL files being archived contains effectively everything in your database, you will want to be sure that the archived data is protected from prying eyes; for example, archive into a directory that does not have group or world read access.
53It is important that the archive command return zero exit status if and only if it succeeds.
54Upon getting a zero result, PostgreSQL will assume that the file has been successfully archived, and will remove or recycle it.
55However, a nonzero status tells PostgreSQL that the file was not archived; it will try again periodically until it succeeds.
56Another way to archive is to use a custom archive module as the archive_library.
57Since such modules are written in C, creating your own may require considerably more effort than writing a shell command.
58However, archive modules can be more performant than archiving via shell, and they will have access to many useful server resources.
59For more information about archive modules, see Chapter 49.
60When the archive command is terminated by a signal (other than SIGTERM that is used as part of a server shutdown) or an error by the shell with an exit status greater than 125 (such as command not found), or if the archive function emits an ERROR or FATAL, the archiver process aborts and gets restarted by the postmaster.
61In such cases, the failure is not reported in pg_stat_archiver.
62Archive commands and libraries should generally be designed to refuse to overwrite any pre-existing archive file.
63This is an important safety feature to preserve the integrity of your archive in case of administrator error (such as sending the output of two different servers to the same archive directory).
64It is advisable to test your proposed archive library to ensure that it does not overwrite an existing file.
65In rare cases, PostgreSQL may attempt to re-archive a WAL file that was previously archived.
66For example, if the system crashes before the server makes a durable record of archival success, the server will attempt to archive the file again after restarting (provided archiving is still enabled).
67When an archive command or library encounters a pre-existing file, it should return a zero status or true, respectively, if the WAL file has identical contents to the pre-existing archive and the pre-existing archive is fully persisted to storage.
68If a pre-existing file contains different contents than the WAL file being archived, the archive command or library must return a nonzero status or false, respectively.
69The example command above for Unix avoids overwriting a pre-existing archive by including a separate test step.
70On some Unix platforms, cp has switches such as -i that can be used to do the same thing less verbosely, but you should not rely on these without verifying that the right exit status is returned.
71(In particular, GNU cp will return status zero when -i is used and the target file already exists, which is not the desired behavior.)
72While designing your archiving setup, consider what will happen if the archive command or library fails repeatedly because some aspect requires operator intervention or the archive runs out of space.
73For example, this could occur if you write to tape without an autochanger; when the tape fills, nothing further can be archived until the tape is swapped.
74You should ensure that any error condition or request to a human operator is reported appropriately so that the situation can be resolved reasonably quickly.
75The pg_wal/ directory will continue to fill with WAL segment files until the situation is resolved.
76(If the file system containing pg_wal/ fills up, PostgreSQL will do a PANIC shutdown.
77No committed transactions will be lost, but the database will remain offline until you free some space.)
78The speed of the archive command or library is unimportant as long as it can keep up with the average rate at which your server generates WAL data.
79Normal operation continues even if the archiving process falls a little behind.
80If archiving falls significantly behind, this will increase the amount of data that would be lost in the event of a disaster.
81It will also mean that the pg_wal/ directory will contain large numbers of not-yet-archived segment files, which could eventually exceed available disk space.
82You are advised to monitor the archiving process to ensure that it is working as you intend.
83In writing your archive command or library, you should assume that the file names to be archived can be up to 64 characters long and can contain any combination of ASCII letters, digits, and dots.
84It is not necessary to preserve the original relative path ( %p) but it is necessary to preserve the file name ( %f).
85Note that although WAL archiving will allow you to restore any modifications made to the data in your PostgreSQL database, it will not restore changes made to configuration files (that is, postgresql.conf, pg_hba.conf and pg_ident.conf), since those are edited manually rather than through SQL operations.
86You might wish to keep the configuration files in a location that will be backed up by your regular file system backup procedures.
87See Section 19.2 for how to relocate the configuration files.
88The archive command or function is only invoked on completed WAL segments.
89Hence, if your server generates only little WAL traffic (or has slack periods where it does so), there could be a long delay between the completion of a transaction and its safe recording in archive storage.
90To put a limit on how old unarchived data can be, you can set archive_timeout to force the server to switch to a new WAL segment file at least that often.
91Note that archived files that are archived early due to a forced switch are still the same length as completely full files.
92It is therefore unwise to set a very short archive_timeout — it will bloat your archive storage. archive_timeout settings of a minute or so are usually reasonable.
93Also, you can force a segment switch manually with pg_switch_wal if you want to ensure that a just-finished transaction is archived as soon as possible.
94Other utility functions related to WAL management are listed in Table 9.97.
95When wal_level is minimal some SQL commands are optimized to avoid WAL logging, as described in Section 14.4.7.
96If archiving or streaming replication were turned on during execution of one of these statements, WAL would not contain enough information for archive recovery.

pg sql dump · 26 steps · 64 source lines not turned into steps (shown grey, listed in the checklist as unmapped)
Source: https://www.postgresql.org/docs/18/backup-dump.html · Rights: PostgreSQL License; https://www.postgresql.org/about/licence/

Procedure text (blue = cited by a step)

7The idea behind this dump method is to generate a file with SQL commands that, when fed back to the server, will recreate the database in the same state as it was at the time of the dump.
8PostgreSQL provides the utility program pg_dump for this purpose.
9The basic usage of this command is:
10$ pg_dump dbname > dumpfile
11As you see, pg_dump writes its result to the standard output.
12We will see below how this can be useful.
13While the above command creates a text file, pg_dump can create files in other formats that allow for parallelism and more fine-grained control of object restoration.
14pg_dump is a regular PostgreSQL client application (albeit a particularly clever one).
15This means that you can perform this backup procedure from any remote host that has access to the database.
16But remember that pg_dump does not operate with special permissions.
17In particular, it must have read access to all tables that you want to back up, so in order to back up the entire database you almost always have to run it as a database superuser.
18(If you do not have sufficient privileges to back up the entire database, you can still back up portions of the database to which you do have access using options such as -n schema or -t table.)
19To specify which database server pg_dump should contact, use the command line options -h host and -p port.
20The default host is the local host or whatever your PGHOST environment variable specifies.
21Similarly, the default port is indicated by the PGPORT environment variable or, failing that, by the compiled-in default.
22(Conveniently, the server will normally have the same compiled-in default.)
23Like any other PostgreSQL client application, pg_dump will by default connect with the database user name that is equal to the current operating system user name.
24To override this, either specify the -U option or set the environment variable PGUSER.
25Remember that pg_dump connections are subject to the normal client authentication mechanisms (which are described in Chapter 20).
26An important advantage of pg_dump over the other backup methods described later is that pg_dump 's output can generally be re-loaded into newer versions of PostgreSQL, whereas file-level backups and continuous archiving are both extremely server-version-specific. pg_dump is also the only method that will work when transferring a database to a different machine architecture, such as going from a 32-bit to a 64-bit server.
27Dumps created by pg_dump are internally consistent, meaning, the dump represents a snapshot of the database at the time pg_dump began running. pg_dump does not block other operations on the database while it is working.
28(Exceptions are those operations that need to operate with an exclusive lock, such as most forms of ALTER TABLE.)
29Text files created by pg_dump are intended to be read by the psql program using its default settings.
30The general command form to restore a text dump is
31$ psql -X dbname < dumpfile
32where dumpfile is the file output by the pg_dump command.
33The database dbname will not be created by this command, so you must create it yourself from template0 before executing psql (e.g., with createdb -T template0 dbname).
34To ensure psql runs with its default settings, use the -X ( --no-psqlrc) option. psql supports options similar to pg_dump for specifying the database server to connect to and the user name to use.
35See the psql reference page for more information.
36Non-text file dumps should be restored using the pg_restore utility.
37Before restoring an SQL dump, all the users who own objects or were granted permissions on objects in the dumped database must already exist.
38If they do not, the restore will fail to recreate the objects with the original ownership and/or permissions.
39(Sometimes this is what you want, but usually it is not.)
40By default, the psql script will continue to execute after an SQL error is encountered.
41You might wish to run psql with the ON_ERROR_STOP variable set to alter that behavior and have psql exit with an exit status of 3 if an SQL error occurs:
42$ psql -X --set ON_ERROR_STOP=on dbname < dumpfile
43Either way, you will only have a partially restored database.
44Alternatively, you can specify that the whole dump should be restored as a single transaction, so the restore is either fully completed or fully rolled back.
45This mode can be specified by passing the -1 or --single-transaction command-line options to psql.
46When using this mode, be aware that even a minor error can rollback a restore that has already run for many hours.
47However, that might still be preferable to manually cleaning up a complex database after a partially restored dump.
48The ability of pg_dump and psql to write to or read from pipes makes it possible to dump a database directly from one server to another, for example:
49$ pg_dump -h host1 dbname | psql -X -h host2 dbname
50The dumps produced by pg_dump are relative to template0.
51This means that any languages, procedures, etc. added via template1 will also be dumped by pg_dump.
52As a result, when restoring, if you are using a customized template1, you must create the empty database from template0, as in the example above.
53After restoring a backup, it is wise to run ANALYZE on each database so the query optimizer has useful statistics; see Section 24.1.3 and Section 24.1.6 for more information.
54For more advice on how to load large amounts of data into PostgreSQL efficiently, refer to Section 14.4.
55pg_dump dumps only a single database at a time, and it does not dump information about roles or tablespaces (because those are cluster-wide rather than per-database).
56To support convenient dumping of the entire contents of a database cluster, the pg_dumpall program is provided. pg_dumpall backs up each database in a given cluster, and also preserves cluster-wide data such as role and tablespace definitions.
57$ pg_dumpall > dumpfile
58The resulting dump can be restored with psql:
59$ psql -X -f dumpfile postgres
60(Actually, you can specify any existing database name to start from, but if you are loading into an empty cluster then postgres should usually be used.) It is always necessary to have database superuser access when restoring a pg_dumpall dump, as that is required to restore the role and tablespace information.
61If you use tablespaces, make sure that the tablespace paths in the dump are appropriate for the new installation.
62pg_dumpall works by emitting commands to re-create roles, tablespaces, and empty databases, then invoking pg_dump for each database.
63This means that while each database will be internally consistent, the snapshots of different databases are not synchronized.
64Cluster-wide data can be dumped alone using the pg_dumpall --globals-only option.
65This is necessary to fully backup the cluster if running the pg_dump command on individual databases.
66Some operating systems have maximum file size limits that cause problems when creating large pg_dump output files.
67Fortunately, pg_dump can write to the standard output, so you can use standard Unix tools to work around this potential problem.
68There are several possible methods:
69Use compressed dumps.
70You can use your favorite compression program, for example gzip:
71$ pg_dump dbname | gzip > filename.gz
72$ gunzip -c filename.gz | psql dbname
73$ cat filename.gz | gunzip | psql dbname
74Use split.
75The split command allows you to split the output into smaller files that are acceptable in size to the underlying file system.
76For example, to make 2 gigabyte chunks:
77$ pg_dump dbname | split -b 2G - filename
78$ cat filename* | psql dbname
79If using GNU split, it is possible to use it and gzip together:
80$ pg_dump dbname | split -b 2G --filter='gzip > $FILE.gz'
81It can be restored using zcat.
82Use pg_dump 's custom dump format.
83If PostgreSQL was built on a system with the zlib compression library installed, the custom dump format will compress data as it writes it to the output file.
84This will produce dump file sizes similar to using gzip, but it has the added advantage that tables can be restored selectively.
85The following command dumps a database using the custom dump format:
86$ pg_dump -Fc dbname > filename
87A custom-format dump is not a script for psql, but instead must be restored with pg_restore, for example:
88$ pg_restore -d dbname filename
89See the pg_dump and pg_restore reference pages for details.
90For very large databases, you might need to combine split with one of the other two approaches.
91Use pg_dump 's parallel dump feature.
92To speed up the dump of a large database, you can use pg_dump 's parallel mode.
93This will dump multiple tables at the same time.
94You can control the degree of parallelism with the -j parameter.
95Parallel dumps are only supported for the "directory" archive format.
96$ pg_dump -j num -F d -f out.dir dbname

7These are the steps to perform an upgrade with pg_upgrade:
8The steps to upgrade logical replication clusters are not covered here; refer to Section 29.13 for details.
9Optionally move the old cluster If you are using a version-specific installation directory, e.g., /opt/PostgreSQL/18, you do not need to move the old cluster.
10The graphical installers all use version-specific installation directories.
11If your installation directory is not version-specific, e.g., /usr/local/pgsql, it is necessary to move the current PostgreSQL install directory so it does not interfere with the new PostgreSQL installation.
12Once the current PostgreSQL server is shut down, it is safe to rename the PostgreSQL installation directory; assuming the old directory is /usr/local/pgsql, you can do: to rename the directory.
13$ mv /usr/local/pgsql /usr/local/pgsql.old
14For source installs, build the new version Build the new PostgreSQL source with configure flags that are compatible with the old cluster. pg_upgrade will check pg_controldata to make sure all settings are compatible before starting the upgrade.
15Install the new PostgreSQL binaries Install the new server's binaries and support files. pg_upgrade is included in a default installation.
16For source installs, if you wish to install the new server in a custom location, use the prefix variable:
17$ make prefix=/usr/local/pgsql.new install
18Initialize the new PostgreSQL cluster Initialize the new cluster using initdb.
19Again, use compatible initdb flags that match the old cluster.
20Many prebuilt installers do this step automatically.

22Install extension shared object files Many extensions and custom modules, whether from contrib or another source, use shared object files (or DLLs), e.g., pgcrypto.so.
23If the old cluster used these, shared object files matching the new server binary must be installed in the new cluster, usually via operating system commands.
24Do not load the schema definitions, e.g., CREATE EXTENSION pgcrypto, because these will be duplicated from the old cluster.
25If extension updates are available, pg_upgrade will report this and create a script that can be run later to update them.
26Copy custom full-text search files Copy any custom full text search files (dictionary, synonym, thesaurus, stop words) from the old to the new cluster.
27Adjust authentication pg_upgrade will connect to the old and new servers several times, so you might want to set authentication to peer in pg_hba.conf or use a ~/.pgpass file (see Section 32.16).
28Stop both servers Make sure both database servers are stopped using, on Unix, e.g.: or on Windows, using the proper service names: Streaming replication and log-shipping standby servers must be running during this shutdown so they receive all changes.

34Verify that the “ Latest checkpoint location ” values match in all clusters.
35Also, make sure wal_level is not set to minimal in the postgresql.conf file on the new primary cluster.
36Run pg_upgrade Always run the pg_upgrade binary of the new server, not the old one. pg_upgrade requires the specification of the old and new cluster's data and executable ( bin) directories.
37You can also specify user and port values, and whether you want the data files linked, cloned, or swapped instead of the default copy behavior.
38If you use link mode, the upgrade will be much faster (no file copying) and use less disk space, but you will not be able to access your old cluster once you start the new cluster after the upgrade.
39Link mode also requires that the old and new cluster data directories be in the same file system.
40(Tablespaces and pg_wal can be on different file systems.) Clone mode provides the same speed and disk space advantages but does not cause the old cluster to be unusable once the new cluster is started.
41Clone mode also requires that the old and new data directories be in the same file system.
42This mode is only available on certain operating systems and file systems.
43Swap mode may be the fastest if there are many relations, but you will not be able to access your old cluster once the file transfer step begins.
44Swap mode also requires that the old and new cluster data directories be in the same file system.
45Setting --jobs to 2 or higher allows pg_upgrade to process multiple databases and tablespaces in parallel.
46A good starting point is the number of CPU cores on the machine.
47This option can substantially reduce the upgrade time for multi-database and multi-tablespace servers.
48For Windows users, you must be logged into an administrative account, and then run pg_upgrade with quoted directories, e.g.: Once started, pg_upgrade will verify the two clusters are compatible and then do the upgrade.
49You can use pg_upgrade --check to perform only the checks, even if the old server is still running. pg_upgrade --check will also outline any manual adjustments you will need to make after the upgrade.
50If you are going to be using link, clone, copy-file-range, or swap mode, you should use the option --link, --clone, --copy-file-range, or --swap with --check to enable mode-specific checks. pg_upgrade requires write permission in the current directory.
51Obviously, no one should be accessing the clusters during the upgrade. pg_upgrade defaults to running servers on port 50432 to avoid unintended client connections.
52You can use the same port number for both clusters when doing an upgrade because the old and new clusters will not be running at the same time.
53However, when checking an old running server, the old and new port numbers must be different.
54If an error occurs while restoring the database schema, pg_upgrade will exit and you will have to revert to the old cluster as outlined in Step 17 below.
55To try pg_upgrade again, you will need to modify the old cluster so the pg_upgrade schema restore succeeds.
56If the problem is a contrib module, you might need to uninstall the contrib module from the old cluster and install it in the new cluster after the upgrade, assuming the module is not being used to store user data.

72Run rsync When using link mode, standby servers can be quickly upgraded using rsync.

74The directory structure under the specified directories on the primary and standbys must match.
75Consult the rsync manual page for details on specifying the remote directory, e.g., You can verify what the command will do using rsync 's --dry-run option.
76While rsync must be run on the primary for at least one standby, it is possible to run rsync on an upgraded standby to upgrade other standbys, as long as the upgraded standby has not been started.
77What this does is to record the links created by pg_upgrade 's link mode that connect files in the old and new clusters on the primary server.
78It then finds matching files in the standby's old cluster and creates links for them in the standby's new cluster.

89(You do not need to run pg_backup_start() and pg_backup_stop() or take a file system backup as the standbys are still synchronized with the primary.) 95It will also generate script files that must be run by the administrator.

9This means it may not be possible for one Python installation to meet the requirements of every application.

11The solution for this problem is to create a virtual environment, a self-contained directory tree that contains a Python installation for a particular version of Python, plus a number of additional packages.
12Different applications can then use different virtual environments.
13To resolve the earlier example of conflicting requirements, application A can have its own virtual environment with version 1.0 installed while application B has another virtual environment with version 2.0.
14If application B requires a library be upgraded to version 3.0, this will not affect application A’s environment.
15The module used to create and manage virtual environments is called venv. venv will install the Python version from which the command was run (as reported by the --version option).
16For instance, executing the command with python3.12 will install version 3.12.
17To create a virtual environment, decide upon a directory where you want to place it, and run the venv module as a script with the directory path:
18$ python -m venv tutorial-env
19This will create the tutorial-env directory if it doesn’t exist, and also create directories inside it containing a copy of the Python interpreter and various supporting files.
20A common directory location for a virtual environment is.venv.
21This name keeps the directory typically hidden in your shell and thus out of the way while giving it a name that explains why the directory exists.
22It also prevents clashing with.env environment variable definition files that some tooling supports.

43$ deactivate
